# Strong Skills 0.4.3-preview.1 预览版

> 本版不新增常驻工具：默认仍是 6 个入口，开启 Shell 后 7 个。重点是让开启后的 Shell 真正被 AI 使用、接入 DSH 沙箱、恢复 64 KiB 输出的首尾信息，并把联网搜索从串行等待改为并发竞速；常驻提示词再降约 22%。

0.4.3-preview.1 是 0.4.3 线的预览版。0.4.2 的 Bing 解包、Shell 超时收尾、点击校验与 PTC 截图修复全部保留；本版不改变工具名、参数或配置字段，升级后不需要迁移 profile。

### AI 直接使用 strong_shell

开启「Shell 工具」后，插件做两件事：

1. 在常驻策略中加入路由：所有 shell 命令直接用 `strong_shell`，使用设置中的后端，不要改用宿主原生 bash/pwsh，也不要询问用户选哪个。
2. 安装 `tools/pre-execute` 拦截：当宿主原生 `bash`/`pwsh` 被调用、`strong_shell` 对当前 Agent 可见时，返回 `deny` 并说明改用 `strong_shell`。这针对每一次调用，而不是只提示一次。

以下情况不拦截：Shell 设置关闭、`strong_shell` 被工具限制隐藏、执行没有 Agent、宿主不提供 `ctx.on`/`ctx.tools`。因此旧宿主和关闭 Shell 的用户保持原行为。独立 MCP 服务没有 DSH 会话，不经过该拦截；它的 Shell 边界见下文。内置 Bash 的固定后端同样适用，AI 不会再被要求二选一。

### Shell 继承 DSH 沙箱

`strong_shell` 每次执行都会解析当前会话的沙箱策略：

- 会话为 `danger-full-access`：按原行为以当前用户权限执行，并在结果中标记 `sandbox.enforced: false`。
- `read-only` / `workspace-write`：把启动参数交给宿主 `ctx.sandbox.confine(...)`，用返回的受限启动命令运行；结果包含 `sandbox.mode`、`enforcement`、`denied`，stderr 命中拒绝签名时 `denied: true`。
- 缺少沙箱服务或 `workspaceRoot`：返回 `SANDBOX_UNAVAILABLE`，不执行命令。不会因为拿不到沙箱就退回无约束执行。
- 内置 Bash：只读模式下直接拒绝内置写入命令；外部程序同样经过沙箱包装。

Windows ACL 模式的 `enforcement` 为 `partial`，这是宿主实现的边界；插件不再声称自己“完全隔离”。

### 独立 MCP 的 Shell 边界

独立 stdio MCP 服务没有 DSH 会话，也就没有 `sandboxPolicy` 或宿主 `ctx.sandbox`。只有显式传入 `--shell on` 才会注册 `strong_shell`；此时命令以当前用户权限运行，初始化提示词会明确说明这一点，并建议需要沙箱时改用原生插件。默认关闭，README 的 MCP 与安全边界已同步标注。

### Windows 沙箱兼容

DSH 的 Windows ACL 受限令牌运行器无法启动 Git Bash：直接探测宿主运行器时，MSYS 报 `couldn't create signal pipe, Win32 error 5`（状态 3221225794），只读与工作区写入模式都一样；Windows PowerShell 5.1 可以在同一沙箱中运行。这与 DSH 上游讨论 #7877、#8209 记录的宿主限制一致。

因此：

- 受限模式下 `auto` 在 Windows 直接使用插件内置 Bash，不再先尝试 Git Bash 后得到空输出。
- 固定 `git-bash` 会返回 `SHELL_UNAVAILABLE`，说明原因，并提示改选内置 Bash、PowerShell，或切换会话权限；插件不会把它放到沙箱外执行。
- `pwsh` 仍优先 PowerShell 7，找不到时回退 Windows PowerShell 5.1。
- 沙箱运行器是 Electron 可执行文件时，插件为它补回 `ELECTRON_RUN_AS_NODE=1` 与宿主 `NODE_OPTIONS` preload，避免 Electron 静默启动后以空输出退出。
- 内置 Bash 新增 `printf`、`seq` 与 `exit`，常见脚本不再落到沙箱下无法启动的 MSYS 可执行文件。


### 输出、后台与编码

- 每路输出最多 64 KiB，超出时保留前 1/4 与后 3/4，并插入“[truncated: 已省略 N 字节，保留开头与末尾]”标记。
- `StrongEngine` 直接返回 `strong_shell` 结果，不再被 `maxOutputChars` 二次截断。此前 `thorough`（12,000）下实际只有约 9.4K 字符；现在 64 KiB 收集器的上限真正生效。
- 直接子进程退出后只等待短暂排空即完成；`sleep 4 & echo started` 不再拖到超时。`command & wait` 仍按超时路径终止。
- 输出先按严格 UTF-8 解码，失败后尝试 GBK，再退回有损 UTF-8；`chcp 936` 的中文不再乱码。

### 搜索并发竞速

`strong_web` 原来先等 DuckDuckGo 15 秒，失败后才请求 Bing。现在两个引擎同时发起，首个非空解析获胜并中止另一方；单引擎 4 秒、整次 8 秒。实测 5 个未命中缓存的查询，中位总耗时从 11,079 ms 降到 251 ms，首条 URL 与原实现一致。页面打开仍是 15 秒 / 2 MB，并保留 SSRF、DNS 与按项目根隔离的缓存。

### 安装与升级

桌面端「插件 → 添加插件」使用固定版本来源，安装后完全退出并重新打开 DSH：

```text
github:wemebabo57-a11y/dsh-mcp-strong-and-skills#0.4.3-preview.1
```

web profile：

```sh
dsh plugin --profile web add github:wemebabo57-a11y/dsh-mcp-strong-and-skills#0.4.3-preview.1
dsh --profile web
```

本机 desktop profile 的依赖请继续保持浮动（不要加 `#tag`），这样 DSHMarket 会按默认分支 `package.json` 的版本发现更新。

需要 **Node.js 24.9+** 与 **DSH 0.2.1-rc.3 或同一兼容范围内的更新版本**。

### 验证情况

- 197 项自动化测试、`node --test` 全部通过；`node scripts/check.mjs` 与 `node scripts/build-ui.mjs --check` 通过。
- 新增覆盖：原生 bash/pwsh 拦截及四类跳过条件、沙箱包装与缺少 provider 的失败关闭、Windows 受限模式回退到内置 Bash 与固定 Git Bash 的明确报错、Electron 运行器环境、只读内置写入拒绝、70,000 字节输出的首尾保留、后台 `sleep 4 &` 快速返回、GBK 字节解码、内置 `printf`/`seq`/`exit`、搜索并发与调用方取消。
- 真实网络：5 个查询基准，中位 11,079 ms → 251 ms；结果与首条 URL 一致。
- 真实模型：用 DSH 0.2.1-rc.3 无头会话加载本仓库插件，共发送四条短指令。未点名工具时模型自行选择 `strong_shell`；后端为内置 Bash，会话处于 `workspace-write`，结果 `sandbox.enforced: true`，stdout 正确。显式要求 `strong_shell` 的指令通过；固定 `pwsh` 后端经 Windows PowerShell 5.1 在沙箱内返回正确输出；固定 `git-bash` 后端返回 `SHELL_UNAVAILABLE`，模型没有尝试在沙箱外执行。
- 限制：Windows ACL 沙箱的 `enforcement` 为 `partial`，不覆盖所有对象类型；Git Bash 在受限令牌下无法启动是宿主限制，不是插件可以修复的；内置 Bash 是 POSIX 子集，不是完整 Bash，新增 `printf`/`seq`/`exit` 后仍可能缺少 `sed`/`awk` 等工具。本次真实会话未覆盖宿主原生 bash/pwsh 拦截路径，因为该 Windows 宿主没有注册原生 shell；该路径由单元测试覆盖。
